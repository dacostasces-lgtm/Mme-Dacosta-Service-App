# 7 octobre 2026 — la base de production a été écrasée

## Ce qui s'est passé

Un `supabase db reset --linked` lancé depuis le dépôt d'un **autre** projet,
alors que le projet lié était celui de Madame Dacosta
(`ghujpeuckfjcuvlxjmuf`), a supprimé le schéma `public`, vidé `auth.users`,
puis rejoué les migrations de cet autre dépôt.

`--linked` ne désigne rien de stable : il lit `supabase/.temp/project-ref`,
écrit par le dernier `supabase link` passé dans ce répertoire. Rien dans la
commande ne nomme sa cible, et rien ne la montre avant qu'elle n'agisse.

## Constats, vérifiés un par un

| Constat | Résultat |
|---|---|
| Page Offres en production | « Could not find the table `public.jobs` » |
| Projet Supabase du site (lu dans le bundle public) | `ghujpeuckfjcuvlxjmuf` |
| Tables dans `public` | 14, appartenant à l'autre projet (`listings`, `boosts`, `wallets`, `private_media_unlocks`…) |
| Tables de Madame Dacosta | **0** |
| Historique des migrations `2026…` | **0 entrée**, remplacé par `0001`→`0016` |
| `auth.users` | **0** |
| Lignes dans les tables de l'autre projet | **0 partout** — il n'avait fait qu'initialiser le schéma |
| Buckets `avatars` et `cvs` | **intacts**, 2 fichiers survivants |

Les buckets sont la signature du projet : ils sont créés par
`20260728030000_storage_buckets.sql`. C'était donc bien le bon projet, dont le
schéma a été remplacé.

## Perdu définitivement

`supabase backups list` répond `pitr_enabled: false` et `backups: []` — le
forfait gratuit ne conserve aucune sauvegarde. Rien à restaurer.

Sont perdus : les 5 comptes et leurs profils, les offres, les candidatures,
les réservations, les abonnements, les messages, et l'historique de
modération. Survivent : les deux fichiers d'une candidate (`avatar.jpg`,
`cv.pdf`), désormais orphelins.

Les réglages du projet ne sont **pas** dans la base et survivent : Site URL,
Redirect URLs, SMTP Resend, modèles d'emails, gabarits. Rien à refaire de ce
côté.

## Reconstruction

Le schéma se rebâtit entièrement depuis les migrations du dépôt, qui sont
intactes. C'est d'ailleurs ce que `scripts/e2e.sh` fait à chaque passage —
`supabase db reset` rejoue les 28 migrations depuis zéro — et la suite était à
25/25 juste avant l'incident. La chaîne est donc prouvée.

```bash
# 1. S'assurer de viser le bon projet. Ne jamais sauter cette étape.
./scripts/verifier-projet.sh

# 2. Rebâtir. Détruit ce qui est là — à cette date, les tables vides de
#    l'autre projet, et rien d'autre.
supabase db reset --linked

# 3. Vérifier.
./scripts/verifier-projet.sh && supabase migration list --linked
```

`20260728030000` est idempotente (`ON CONFLICT DO UPDATE` sur les buckets,
`DROP POLICY IF EXISTS` avant chaque politique), donc les buckets survivants
ne la font pas échouer. `20260730000000` réinsère les villes et les quartiers,
qui n'ont donc pas à être ressaisis.

### Après la reconstruction

1. **Recréer le compte d'administration.** `profiles.role` est gelé par
   `protect_profile_columns` : il faut s'inscrire normalement, puis passer le
   rôle à `admin` en base. Sans cela, `/admin` est inatteignable et aucun
   profil ne peut être publié.
2. **Supprimer les deux fichiers orphelins** des buckets `avatars` et `cvs` :
   leur propriétaire n'existe plus.
3. **Vérifier que l'historique des migrations ne mélange plus** les `0001`→
   `0016` avec les `2026…`.

## Pour que cela ne se reproduise pas

Par ordre d'efficacité réelle :

1. **Une sauvegarde.** C'est la seule mesure qui aurait rendu l'incident
   réparable, et la seule qui protège contre la même erreur commise depuis un
   autre dépôt. Le forfait Pro inclut des sauvegardes quotidiennes ; le Point
   in Time Recovery est une option au-dessus. Tant qu'il n'y en a pas, chaque
   erreur de ce genre est définitive.
2. **Donner à l'autre projet son propre projet Supabase.** Tant que les deux
   dépôts peuvent se lier au même, l'erreur reste à un `supabase link` de
   distance.
3. **`./scripts/verifier-projet.sh` avant toute commande distante.** Il compare
   le projet lié à `supabase/projet-production` et refuse sinon. Il ne protège
   que ce dépôt : le même garde-fou est à poser dans l'autre.
